# TravelBuddy corrected-source report

## What was corrected

### Firebase authorization and mode switching
- `role` remains the security role (`USER` / `ADMIN`).
- `currentMode` remains the travel mode (`PASSENGER` / `DRIVER`).
- Passenger/Driver switching uses one partial Firestore write to `users/{uid}.currentMode` and never changes `role` or `defaultRolePreference`.
- Home no longer optimistically changes the visible mode before Firebase confirms the write.
- The user profile stream now follows FirebaseAuth across app startup, login, logout and process/session restoration.
- Firestore rules no longer use Passenger/Driver mode as a server-side privilege gate for creating a ride/request. Ownership is the security boundary.

### Authentication/session persistence
- FirebaseAuth is the startup source of truth and is observed using an AuthStateListener.
- Auth has explicit `Loading`, `Authenticated`, and `Unauthenticated` states so startup does not treat Firebase initialization as logout.
- A restored Firebase session goes to Home instead of requiring password entry again.
- Sign-out is explicit from Profile only.
- Removed client-side hard-coded email addresses that could self-grant ADMIN.
- Google Credential Manager flow uses `default_web_client_id` generated by Firebase configuration; there is no hard-coded OAuth client fallback.

### Firestore/profile
- Profile saves use partial updates only and cannot overwrite `uid`, `email`, `employeeId`, `role`, or `currentMode`.
- Read-only email comes from FirebaseAuth first, then Firestore fallback.
- Profile edit draft is synchronized from the loaded Firestore profile.
- Added visible travel preferences and seat preference editing.
- Reminder/mute changes now report failures instead of silently showing success.

### Ride lifecycle
- Ride creation uses authenticated UID as `driverId` instead of trusting stale UI objects.
- Ride updates preserve created/started/completed timestamps.
- Added `OFFLINE` to allowed ride lifecycle rules.
- Seat acceptance remains a Firestore transaction and validates driver ownership/request state/available seats.
- Driver rejection records response time.
- Finishing a ride marks accepted requests `COMPLETED` in the same batch.
- Normal drivers no longer attempt to write Admin-only `co2Records`; Spark-plan Admin analytics derives CO2 from completed rides + `systemConfig`.

### Passenger discovery / commute UI
- Removed reference/mock values such as fixed EMs/Plant/date/time/counts from production Home UI.
- Commute selection now stores an actual date, direction, stable commute-window name, pickup and destination.
- Change Commute opens a real Material3 bottom sheet with date picker, direction-aware windows, pickup and destination choices.
- Hero card displays selected commute data and the approved `home_commute_hero.png` asset.
- Pickup groups are calculated from real filtered ride data and all real groups are rendered; demo A/B-block cards are gone.
- Pickup-group cards open a real driver detail sheet.
- “Request Ride” in that detail sheet now calls `RideRepository.requestRideFromDriver()` instead of only dismissing the sheet.
- Personal impact uses completed passenger rides and configured sustainability factors; demo figures are removed.

### Activity
- Activity now loads full passenger request history and driver ride history rather than only today's passenger requests.
- All / Passenger / Driver filters are now actually clickable.

### Admin module
- Admin remains isolated to the Admin navigation destination.
- Replaced co2Records-dependent dashboard with live aggregation from users/rides/requests/system config.
- Overview includes registered users, active participants, completed rides, CO2, operational counts and user-mode counts.
- User management can promote/demote other users without changing their travel mode and prevents self-demotion in the UI/repository.
- Analytics ranks driver and passenger contribution without changing the overall system CO2 calculation.

### Resources/UI
- Uses approved PNG resources already present under `app/src/main/res/drawable-nodpi/`.
- Hero/impact asset opacity and positioning were adjusted.
- Removed remaining empty `onClick = {}` callbacks found in production source.
- Status chips include OFFLINE and EXPIRED states.

## Firebase rules
Publish the included `firestore.rules` to the same Firebase project used by `google-services.json` before testing the corrected client.

Important rule behavior:
- Normal registration always creates `role=USER`.
- A user can modify only approved own-profile fields; role/identity fields remain immutable.
- Admin can change another user's `role` only.
- Any authenticated employee may offer/request a ride as themselves; travel mode is UX state, not an authorization privilege.
- Ride/request ownership and status transitions remain protected.
- `systemConfig` is readable to signed-in users for personal impact calculations but writable only by Admin.
- `co2Records` and `adminAnalytics` remain Admin-only.

## Google sign-in manual setup
Code is prepared for Credential Manager + Firebase Auth, but Google login also requires Firebase/Google console configuration:
1. Enable Google provider in Firebase Authentication.
2. Add the debug/release SHA certificate fingerprints for the Android app.
3. Download the refreshed `google-services.json` if Firebase changes OAuth clients and place it in `app/google-services.json`.
4. Rebuild and verify `default_web_client_id` is generated.

Do not hard-code an OAuth client ID into Kotlin source.
